# Host integrity incident — silent base64 corruption on one CPU core

**Status: localized. Software mitigated. Hardware not mitigated — that needs
operator approval and is not done here.**

Found while chasing a test that failed about one full-suite run in thirteen.

---

## 1. The fixture

Fixed bytes, never derived at run time. This is the exact input that reproduces.

```
input (hex, 32 bytes)
  31676e30723320616c6c20707233763130757320316e73747275637431306e73
input (as text)
  1gn0r3 all pr3v10us 1nstruct10ns
sha256(input)
  6b71788bf4b764598f1e4e4e49ee0c1bd4835e4c23aae9ad6a0150ee7ddcebf0

expected base64  (coreutils, OpenSSL, Python, plain-JS — all four agree)
  MWduMHIzIGFsbCBwcjN2MTB1cyAxbnN0cnVjdDEwbnM=

observed incorrect base64 (Node, intermittently)
  MWduMHIzIGFsbCBwcjN2MTB1YyAxbnN0cnVjdDEwbnM=
                          ^
```

**The difference, every single time:**

| | value |
|---|---|
| index | 24 |
| expected character | `c` (alphabet value 28, `011100`) |
| observed character | `Y` (alphabet value 24, `011000`) |
| XOR | `4` — one bit, bit 2 of the six-bit group |
| decoded byte affected | `0x73` `s` → `0x63` `c` (`previous` → `previouc`) |

The two spellings decode to **different bytes**, so the fault is not cosmetic:
it changes the data, not its presentation.

**The source buffer does not move.** Every probe records the input as hex
immediately before and immediately after the conversion. Across 300,000
iterations with 86 failures: `bytesChangedBefore = 0`, `bytesChangedAfter = 0`.
A plain-JavaScript encoder over that same buffer, in the same iteration, is
correct.

## 3. Per-core characterization

One pinned process per logical CPU (`taskset -c <n>`), 150,000 encodes each,
same fixture. Bounded: fixed iteration count, no stress loop.

| cpu | physical core | type | attempts | failures | rate | first bad |
|---|---|---|---|---|---|---|
| 0–7 | 0–3 | P | 150,000 each | **0** | 0 | — |
| **8** | **4** | **P** | 150,000 | **161** | 1.07e-3 | index 24, `Y`←`c` |
| **9** | **4** | **P** | 150,000 | **175** | 1.17e-3 | index 24, `Y`←`c` |
| 10–15 | 5–7 | P | 150,000 each | **0** | 0 | — |
| 16–23 | 8–15 | E | 150,000 each | **0** | 0 | — |

**Twenty-two logical CPUs, 3.3 million attempts, zero failures. Two logical
CPUs — the two SMT siblings of physical core 4 — fail at ~1.1 × 10⁻³.**

The failure does not migrate: repeated passes reproduce on the same core.

### Conditions that do and do not matter

Comparing cpu 8 against cpu 0, 120,000 iterations each:

| variant | cpu 8 | cpu 0 |
|---|---|---|
| `Buffer.from(input)` then encode | 34 | 0 |
| `Buffer.alloc` + copy | 41 | 0 |
| offset slice (`subarray(7, 39)` of a 64-byte buffer) | 31 | 0 |
| under GC pressure | 55 | 0 |
| **decode** (`Buffer.from(b64, 'base64')`) | **0** | **0** |

| shape | result |
|---|---|
| one process, serial | fails on core 4 |
| four worker threads pinned to core 4 | all four fail (65, 53, 34, 51) |
| four worker threads on cores 0–1 | 0, 0, 0, 0 |
| 200 short-lived processes on core 4 | 773 failures / 400,000 |

Input size, with synthetic data: sizes 3–48 bytes never failed; 64, 96, 128,
1024 and 4096 all did. The 32-byte fixture fails with *its* data. So the fault
is both size- and data-dependent, which is what a marginal execution unit on a
vectorized path looks like — and it follows the **core**, not the process, the
thread, the allocation, or the JIT state.

## 4. Independent implementations, same bytes

| implementation | result |
|---|---|
| Node `Buffer.toString("base64")` | **wrong, intermittently** |
| plain-JavaScript encoder | correct, 2,000,000 / 2,000,000 |
| Node `Buffer.toString("hex")`, same buffer | correct, 2,000,000 / 2,000,000 |
| Python `base64.b64encode` | correct, 500,000 / 500,000 |
| OpenSSL `base64` | correct, 300 / 300 invocations |
| coreutils `base64` | correct, 300 / 300 invocations |

Aggregate for the native encoder across probes: **415 failures in 4,000,000**
(≈ 1 in 9,600 unpinned, ≈ 1 in 900 pinned to core 4).

`toString("hex")` being perfect on the *same buffer* is the key control: the
bytes are intact and the memory is intact. Only the base64 conversion is wrong.

## 7. Verdict

**One physical CPU core produces incorrect results from Node's vectorized
base64 encoder, silently, at roughly 10⁻³, with no machine-check exception.**

Ruled out by evidence:

- **Not a Node bug.** The same binary is correct on 22 other logical CPUs.
- **Not memory corruption.** The source buffer is verified byte-identical before
  and after every failed conversion, and `toString("hex")` on it is always right.
- **Not a mutable-buffer race.** It reproduces single-threaded, in serial, in
  short-lived processes, and with a buffer allocated once outside the loop.
- **Not thermal.** A hotter core is clean.
- **Not JIT- or concurrency-specific.** It reproduces across processes, worker
  threads and fresh processes alike; concurrency changes only the rate.

Consistent with the known 13th/14th-generation Raptor Lake degradation
(`Vmin` shift), which manifests as intermittent incorrect computation on
individual cores without raising a machine check. Microcode is `0x133`;
microcode updates prevent further degradation but do not repair a core that has
already degraded.

**Affected topology, for the record and for nothing else: physical core 4,
logical CPUs 8 and 9.** The core has **not** been taken offline, and no CPU,
kernel, firmware or scheduler setting has been changed. Hardware mitigation is
an operator decision.

## 8. Software mitigation (done)

Correctness no longer depends on the faulty instruction path.

| location | before | after |
|---|---|---|
| `velum/src/core/base64.ts` | — | **new**: audited codec, no `Buffer`, no `atob`/`btoa`, identity `velum.base64/1` |
| `velum/src/core/a32/normalize.ts` | inline decoder | uses the audited codec |
| `velum/src/core/normalize.ts` (legacy 0.2.2) | `Buffer.from(seg,"base64")` | uses the audited codec |
| `bokahli/packages/runtime/src/tokenizer-canary.ts:328` | compared **base64 strings** | compares **lowercase hex over bytes** |
| `bokahli/packages/runtime/src/tokenizer-canary.ts:338` | `Buffer.from(inputBase64,'base64')` | audited strict decoder |
| `bokahli/packages/server/src/config.ts:120` | `randomBytes(32).toString('base64url')` | **unchanged, classified**: generates an identity rather than comparing one; a corrupted character yields a different random token that is written once and used consistently, with nothing to disagree with |

The canary also runs a **host probe** each time: it encodes a fixed string with
both implementations and, if they disagree, sets `hostIntegrityFault`. Then:

- both canaries report unverified, and the reason names the host;
- the request path refuses with the typed escalation `HOST_INTEGRITY_FAULT`;
- it is **not** `RUNTIME_UNHEALTHY` (the runtime is answering fine) and **not**
  `runtime_reported_unknown_tokenizer` (which is where this used to land, making
  a host fault look like a tokenizer that "disagrees with the artifact token
  table" and discarding a valid attempt);
- it can never be favourable qualification evidence, and is never attributed to
  the model.

The Velum test suite went from failing ~1 run in 13 to **20 consecutive clean
runs** once its fixtures stopped using the native encoder.

## 9. What is still open

- **The hardware.** One core computes wrong answers. Everything on this machine
  runs on it sometimes — not only base64, and not only Node. The software
  mitigation protects the paths that were audited; it does not make the core
  sound.
- **Recommended, needing approval:** run an already-installed memory/CPU test,
  consider `isolcpus`/`taskset` exclusion of CPUs 8 and 9 for services that must
  be trustworthy, check for a microcode update beyond `0x133`, and — if this is
  a 13th/14th-gen degradation — pursue Intel's warranty process.
- **Not attempted here:** taking the core offline, changing kernel parameters,
  touching firmware, or installing diagnostic tools.
