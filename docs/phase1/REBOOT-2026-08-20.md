## What it could not see

The reboot came up **without the GPU**, and served that way for the next 17
minutes without a single check noticing.

```
06:18:41.583  nvidia            module loaded
06:18:48.520  /dev/nvidia0, /dev/nvidiactl created
06:18:49.533  bokahli-runtime.service starting
06:18:49.703  E ggml_cuda_init: failed to initialize CUDA: unknown error
06:18:49.704  warning: no usable GPU found, --gpu-layers option will be ignored
06:18:50.935  nvidia_uvm        module loaded      <-- 1.232 s too late
06:18:50.936  /dev/nvidia-uvm created
```

`nvidia_uvm` is loaded lazily by the setuid helper `/usr/bin/nvidia-modprobe`, on
behalf of the first process that opens a CUDA context. `bokahli-runtime.service`
ran with `NoNewPrivileges=true`, which defeats setuid — so it could never load
the module itself. It silently depended on some *other* GPU consumer going
first. On this boot that consumer was `comfyui.service` (python, started
06:18:51), and it lost the race by 1.2 s.

llama.cpp does not treat that as fatal. It ignored `--n-gpu-layers 999`, loaded
all 12.58 GiB into system RAM, and served correctly:

| Decode | **19.94 tok/s** | 58.9–59.6 tok/s | 62.3 tok/s |
| `llama-server` VmRSS | 13 811 436 kB | ~2.4 GiB on device | — |
| VRAM held by the backend | none — absent from `nvidia-smi` | 2 418 MiB | ~2.4 GiB |

A 3.1× throughput loss that reports itself as healthy, attested, and correct.
The artifact really was the right artifact; the identity really was attested.
Device placement was simply never part of what "healthy" meant.

## Repair

Two checks now bracket the load, both in `bokahli-runtime.service`:

- `ExecStartPre=scripts/require-gpu.sh` — loads `nvidia_uvm` itself (which is
  why `NoNewPrivileges` is off for this unit alone; `bokahli.service`, the
  network-facing one, keeps it) and then proves CUDA initialises using
  `llama-server --list-devices`, the same `ggml_cuda_init` the server is about
  to run. Bounded by `BOKAHLI_GPU_WAIT_SECONDS`, default 90.
- `ExecStartPost=scripts/assert-gpu-placement.sh` — after the model is loaded and
  answering, asks the driver whether our backend actually holds VRAM. A CPU-only
  `llama-server` never appears in `nvidia-smi --query-compute-apps`.

Either failing fails the unit, so `Restart=on-failure` retries and
`StartLimitBurst=5` stops it after five attempts in 300 s rather than looping.
`BOKAHLI_REQUIRE_GPU=0` opts out deliberately — a CPU load is a choice an
operator may make, not a state the machine may drift into unnoticed.

Both were verified against the live host: the placement assertion correctly
failed the CPU-only process left over from the reboot (pid 2036, "loaded WITHOUT
the GPU"), and correctly passed the GPU-backed process that replaced it
(pid 10365, "holds 2418 MiB of VRAM").

### One trap worth recording

The placement check first looked for an open `/dev/nvidia-uvm` handle in
`/proc/<pid>/fd`. That works in a login shell and fails inside the unit: any
mount-namespacing option — `PrivateTmp`, `ProtectControlGroups`,
`ProtectKernelTunables`, all three of which this unit sets — gives the service a
fresh procfs whose sibling `fd` entries are unreadable. `cmdline` stays readable,
so the pid was found and its descriptors looked empty, which reads exactly like a
CPU-only load. Bisected property by property; the check now asks the driver
instead, which works in both contexts.
